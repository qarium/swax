## Description

Реализовать команду `plan`, которая анализирует различия между локальными (базовыми) спецификациями и текущим состоянием репозитория, и формирует отчёт о влиянии изменений на тестирование.

Логика команды:
1. Клонировать репозиторий во временный каталог (через существующий пакет `git/`)
2. Распарсить свежие спецификации из репозитория (через `openapi/`)
3. Загрузить локальные базовые спецификации (через `openapi/`)
4. Вычислить структурный diff между базовой и текущей спецификациями (новый пакет `openapi/diff`)
5. Классифицировать изменения в эндпоинтах: добавленные / изменённые / удалённые (плюс изменения схем под этими эндпоинтами)
6. Отобразить изменённые эндпоинты на граф отслеживаемости — определить затронутые эндпоинты
7. Отправить в LLM: изменённые + затронутые эндпоинты + контекст (граф и diff) → сформировать Impact Report
8. Вывести отчёт в stdout в формате Markdown

Структурный diff выходит за рамки архитектурного правила ТЗ «только пути API» — но только в аналитическом слое diff. Граф отслеживаемости продолжает хранить только пути. Diff видит методы/параметры/схемы, чтобы точнее идентифицировать изменения, но в отчёт попадают только пути с описанием характера изменений.

## Scope

**In scope:**
- Пакет `openapi/diff`: структурный diff спецификаций через `deepdiff`, классификация изменений (added/modified/removed эндпоинты + детали схем)
- Маппинг изменений на граф отслеживаемости: какие узлы затронуты (прямое изменение + транзитивные зависимости по рёбрам графа)
- Команда `plan` (CLI handler в `commnads/plan`)
- LLM-промпт для генерации Impact Report (Summary, Risk, Modified, Affected, Requirements, Checklist) в `llm/prompts.py`
- Рендеринг отчёта в Markdown в stdout
- Модели pydantic для diff-результата и Impact Report
- Тесты, зеркальные структуре исходников

**Out of scope (отложено в Задачу 3):**
- Команда `update` (инкрементальное обновление графа)
- Инкрементальное обновление узлов графа отслеживаемости
- Сохранение отчёта в файл или историю отчётов
- Опции CLI для формата вывода (`--format`, `--output`) — только stdout Markdown

## Acceptance Criteria

- `swax plan` клонирует репозиторий во временный каталог, сравнивает свежие спецификации с локальными
- Diff корректно идентифицирует добавленные/изменённые/удалённые эндпоинты в обеих спецификациях (Swagger 2.0 и OpenAPI 3.x)
- Изменения схем под `components`/`definitions` корректно атрибутируются к эндпоинтам, которые их используют (через развёрнутые `$ref`)
- Затронутые эндпоинты определяются через граф отслеживаемости: прямой путь + все транзитивно-зависимые пути по рёбрам графа
- LLM получает структурированный контекст (изменения + затронутые эндпоинты + релевантные части графа) и возвращает отчёт в заданной структуре
- Отчёт соответствует шаблону ТЗ (Summary, Risk: HIGH/MEDIUM/LOW, Modified, Affected, Requirements, Checklist)
- Вывод идёт только в stdout в формате Markdown
- При отсутствии изменений отчёт содержит Summary "No changes detected" и Risk LOW
- При отсутствии графа отслеживаемости (`.swax/traceability.yml` не существует) — осмысленная ошибка с подсказкой запустить `discover`
- Все публичные функции и классы имеют docstrings в Google-стиле (согласно conventions)
- Тесты покрывают: классификацию diff, маппинг на граф, рендеринг отчёта, edge-cases (нет изменений, пустые спецификации, нет графа)
- `pytest tests/ -x` проходит, `ruff check swax/` без ошибок

## Risks and Constraints

- **Стоимость LLM** — `plan` отправляет в LLM контекст с изменениями и затронутыми эндпоинтами. При крупных изменениях payload может быть большим. Чёткие промпты и `max_tokens` обязательны
- **Гранулярность diff vs. графа** — Diff видит методы/схемы, граф хранит только пути. Маппинг должен корректно агрегировать несколько изменений на одном пути в одну запись отчёта
- **Качество Risk Assessment** — LLM может возвращать Risk вне {HIGH, MEDIUM, LOW}. Требуется валидация и fallback на MEDIUM при некорректном ответе
- **Транзитивные зависимости** — при большом графе затронутые эндпоинты могут расти экспоненциально. Ограничить глубину или количество затронутых эндпоинтов в контексте LLM
- **Производительность deepdiff** — для очень больших спецификаций требуются `cutoff`-опции (см. `deepdiff.md`)
- **Согласованность базовой спецификации** — если локальная база устарела (не было `update`), отчёт может быть избыточным. Это ожидаемо — `plan` анализирует «как есть»
- **Временный каталог git** — клонирование при каждом вызове `plan`. cleanup обязателен
